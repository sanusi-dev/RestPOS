# RestPOS — Feature Specification (Implementation Version)

> This is the definitive feature list for RestPOS Phase 1. It is derived from URY and ERPNext
> reference codebases, with any feature that contradicts a RestPOS-specific requirement replaced
> by the RestPOS version. Every feature listed here will have an implementation plan in PLAN.md.

---

## A. BACK OFFICE FEATURES

### A1. Restaurant Configuration

| # | Feature | What it does |
|---|---|---|
| 1 | Restaurant setup | The top-level configuration record for the entire restaurant. It ties the system to a specific company and branch, sets the invoice numbering prefix (e.g. "INV-"), and optionally a separate prefix for aggregator orders. It also points to the default menu, the default room, the default tax template, and the restaurant's address. Without this record, the POS cannot operate — every other configuration references it. |
| 2 | Room-wise menu | Allows the restaurant to assign different menus to different physical areas (rooms). For example, the main dining hall might offer the full food menu while the bar area only offers drinks and bar snacks. Each room-to-menu mapping is a simple row in a child table on the restaurant config. When a waiter selects a table in a particular room, the POS automatically loads the menu assigned to that room. If this feature is disabled, all rooms share the same default menu. |
| 3 | Order-type-wise menu | Allows the restaurant to assign different menus based on how the order is placed. For example, delivery orders might offer a reduced menu (only items that travel well), while dine-in offers the full menu. Each order-type-to-menu mapping is a row in a child table. This only applies to non-dine-in order types (Take Away, Delivery, Phone In) — dine-in always uses the room-based menu. When a cashier selects an order type, the POS loads the menu assigned to that type. |
| 4 | Room management | Defines the physical dining areas of the restaurant. Each room belongs to a branch and can be classified as AC or NON-AC. Rooms are the primary way to organise tables — a table always belongs to exactly one room. Rooms also carry their own printer settings, allowing different rooms to route tickets to different printers if needed. For RestPOS, the two key rooms are typically the main dining area and the bar area. |
| 5 | Table management | Defines individual tables within a room. Each table has a name (e.g. "T1"), a seat count, a minimum seating capacity, a shape (Rectangle, Square, or Circle), and a takeaway flag (for virtual "tables" that represent takeaway orders). The system tracks whether a table is currently occupied (has an open order) and the time of the latest invoice. Tables also store visual layout coordinates (x, y, width, height) so they can be displayed on a floor plan. |
| 6 | Table layout editor | A visual drag-and-drop floor plan editor in the back office. The manager can click and drag tables to position them on a grid, resize them, change their shape, and edit their seating capacity. The layout is saved to the database and reflected on the POS table selection screen. This gives staff a realistic visual map of the dining area, making it easy to see which tables are occupied and which are available. The editor supports zoom and pan for large rooms. |
| 7 | Multi-room cashier assignment | Maps staff users (cashiers and waiters) to specific rooms within a branch. A user can be assigned to one or multiple rooms. When a cashier logs in, they only see tables and orders for the rooms they are assigned to. This prevents a bar cashier from accidentally taking orders for the dining room and vice versa. |
| 8 | Branch association | Every staff member must be linked to a branch before they can use the POS. This link is stored as a row in a child table on the branch record. Non-admin users cannot see data from other branches. This ensures data isolation when the system is used across multiple locations. |

### A2. Menu Management

| # | Feature | What it does |
|---|---|---|
| 9 | Menu definition | A named collection of menu items bound to a specific branch. Each menu automatically creates a Price List in the accounting system, which drives the selling prices of its items. A menu can be enabled or disabled — disabling a menu hides all its items from the POS without deleting anything. The restaurant can have multiple menus (e.g. a lunch menu and a dinner menu) and switch between them. |
| 10 | Menu items | Each menu is a collection of items. A menu item links a product from the Item master to the menu and sets its selling rate, its course (e.g. Starters, Mains), whether it is a special dish, and whether it is temporarily disabled. The rate on the menu item is what the customer pays — it overrides any generic Item Price. This is the bridge between the inventory system (which knows about the product) and the POS screen (which shows it to the cashier). |
| 11 | Menu courses | Courses are categories that control the order in which food is prepared and served. For example, a restaurant might define courses like "Starters", "Soups", "Mains", and "Desserts". Each course has a unique serving priority number — a lower number means it should be prepared and served first. When a kitchen ticket prints, items are sorted by course priority so the kitchen knows what to cook first. Courses also appear as filter categories on the POS screen, letting the cashier quickly narrow down the menu. |
| 12 | Special dish flag | Any menu item can be marked as a "special dish". Special dishes get a highlighted filter button on the POS screen, making it easy for the cashier to quickly find the restaurant's featured or recommended items. This is useful for daily specials, chef's recommendations, or high-margin items the owner wants to push. |
| 13 | Item disable | Sometimes a menu item runs out of stock or is temporarily unavailable. Instead of deleting it (which would lose its pricing and course assignment), the manager can simply disable it. A disabled item disappears from the POS screen immediately but remains in the database. When it's back in stock, the manager re-enables it and it reappears. |
| 14 | Item image | Each item can have an attached image. On the POS screen, this image is displayed on the menu card alongside the item name and price. If no image is available, the system shows a placeholder with the first two letters of the item name. Images help cashiers identify items quickly, especially in menus with many similar items. |
| 15 | POS item variants | Allows a single menu item to have selectable variants. For example, a "Chicken" item might have variants for "Quarter", "Half", and "Full". Each variant is a separate Item in the inventory system, linked to the parent via a child table. When the cashier clicks an item with variants on the POS, a dialog appears letting them choose which variant the customer wants. The price updates automatically based on the selected variant. |
| 16 | POS add-on items | Allows items to have optional add-ons that can be upsold. For example, a "Burger" might have add-ons for "Extra Cheese", "Bacon", and "Avocado". Each add-on is a separate Item linked via a child table. When the cashier opens an item's detail dialog, they see a list of available add-ons and can select multiple ones. Each selected add-on is added as a separate line item in the cart with its own price. |
| 17 | Menu-driven pricing | Each menu creates its own Price List in the accounting system. The selling rate is set on the menu item itself, not on a generic Item Price record. This means the same physical item can have different prices in different menus (e.g. a drink might cost less on the lunch menu than on the dinner menu). When an order is placed, the system automatically resolves the correct price list based on which menu is active for the table's room or the order type. |
| 18 | Course serving priority | Each course has a unique integer that controls its serving priority. A priority of 1 means the course should be served first. This number is used to sort items on kitchen tickets — so the kitchen staff can see at a glance what needs to be cooked first. It also sorts items on the POS screen, grouping them by course in the correct order. |
| 19 | Course label on kitchen ticket | A flag on each course that controls whether the course name is printed on the kitchen ticket. For example, you might want "Starters" and "Mains" to appear as labels on the kitchen ticket so the chef knows which items are appetisers vs main courses, but you might not want a label for a generic "Miscellaneous" course. This gives the kitchen clearer context without cluttering the ticket with unnecessary labels. |

### A3. Production / Kitchen Station Configuration

| # | Feature | What it does |
|---|---|---|
| 20 | Production unit | Defines a station in the restaurant that produces items — typically the kitchen or the bar. Each production unit is linked to a POS profile, a branch, and a warehouse. It also has a list of item groups that it handles (e.g. the kitchen handles "Food" items, the bar handles "Beverages"). When an order is placed, the system uses production units to determine where to route kitchen/bar tickets. In RestPOS, production units map directly to the kitchen printer and bar printer — items in the kitchen's item groups print to the kitchen printer, and items in the bar's item groups print to the bar printer. |
| 21 | Production item groups | Tags which categories of items (Item Groups) each production unit handles. For example, the kitchen production unit might handle "Mains", "Starters", and "Soups", while the bar production unit handles "Soft Drinks", "Beer", and "Spirits". When an order contains both food and drinks, the system splits the items and sends only the relevant items to each printer. This is the core routing mechanism that makes departmental split and separate kitchen/bar tickets work. |
| 22 | Block takeaway KOT | An optional setting on a production unit that suppresses ticket printing for takeaway orders. For example, the bar might not need a printed ticket for a takeaway order because the cashier handles the drink directly. When this flag is enabled, only dine-in orders generate a bar ticket; takeaway orders with drinks do not. This reduces unnecessary ticket noise at the bar station. |
| 23 | Production printer assignment | Each production unit is assigned a specific thermal printer. In RestPOS, the kitchen production unit is assigned the kitchen printer's static IP address, and the bar production unit is assigned the bar printer's static IP address. When a ticket is generated, the print agent sends it to the printer assigned to the relevant production unit. This is how the system knows where to send each ticket. |

### A4. POS Profile / Terminal Configuration

| # | Feature | What it does |
|---|---|---|
| 24 | POS profile | The master configuration for a POS terminal or cashier role. It defines: which company and warehouse the terminal operates under, which currency it uses, which selling price list is default, which payment methods are accepted, which item groups are visible, which customer groups are selectable, which print format to use for receipts, which tax template applies, and which cost center to post transactions against. Every order placed on the POS references a POS profile. A restaurant can have multiple profiles (e.g. one for the main cashier, one for the bar). |
| 25 | Cashier permissions | Granular toggles that control what a cashier is allowed to do on the POS. The manager can enable or disable: changing the price of an item (rate change), applying a discount (discount change), switching the warehouse from which stock is deducted, accepting partial payments, and rounding the total to the nearest whole number. These toggles let the owner control how much freedom each cashier has, preventing unauthorised price overrides or excessive discounting. |
| 26 | Stock validation | Controls how and when the system checks whether items are in stock. When `validate_stock_on_save` is enabled, the system checks stock levels only when the cashier saves the order (not on every item click). When `update_stock` is enabled, stock is automatically deducted from the warehouse when the order is submitted (paid). If stock validation is on and an item is out of stock, the cashier sees a warning and cannot complete the order for that item. |
| 27 | Auto-print on order complete | When enabled, the cashier receipt prints automatically the moment an order is submitted and paid. The cashier does not need to click a "Print" button — the print agent receives the job and sends it to the cashier printer immediately. This speeds up the checkout flow and ensures every paid order gets a receipt. |
| 28 | Auto-add scanned item to cart | When enabled, scanning a barcode immediately adds the item to the cart with a quantity of 1, without opening a product dialog. This is useful for high-volume items like bottled drinks where the cashier just scans and moves on. If the item has variants or add-ons, the dialog still opens. |
| 29 | Hide images / unavailable items | Two UI toggles: "Hide images" removes item images from the POS menu cards (useful on slow devices or when images aren't available), and "Hide unavailable items" removes out-of-stock items from the menu entirely so the cashier doesn't accidentally try to order something that can't be served. |
| 30 | Write-off config | Allows the cashier to write off small unpaid balances (e.g. when the customer is 50 naira short and the cashier doesn't want to chase it). The manager configures a maximum write-off limit, a write-off GL account, and a write-off cost center. When the paid amount is slightly less than the total, the difference is posted to the write-off account instead of showing as outstanding. This keeps the books clean without forcing the cashier to collect every last naira. |
| 31 | Action on new invoice | Controls what happens after an order is submitted. The manager can choose: "Always Ask" (prompt the cashier what to do), "Save Changes and Load New" (automatically start a fresh order), or "Discard Changes and Load New" (clear everything and start fresh). This is a workflow speed setting — high-volume restaurants prefer "Discard Changes and Load New" so the cashier is immediately ready for the next customer. |
| 32 | Set grand total to default payment method | When enabled, the total amount of the order is automatically filled into the default payment method's input field when the payment dialog opens. The cashier only needs to confirm and click "Pay". If the customer is paying with a different method or splitting the payment, the cashier can manually adjust. This saves a keystroke in the most common case (full payment in cash). |
| 33 | Restaurant-specific invoice numbering | Uses a restaurant-specific prefix for invoice numbers (e.g. "REST-0001", "REST-0002") instead of a generic ERPNext prefix. The prefix is set on the restaurant configuration and applied to every POS invoice created. This makes it easy to identify restaurant sales in the accounting system and avoids number collisions with other business units. |
| 34 | KOT naming series | A configurable naming pattern for kitchen order ticket numbers. For example, "KOT-####" would produce KOT-0001, KOT-0002, etc. The naming series is set on the POS profile and applied to all KOTs generated from that terminal. A separate "CNCL-" prefix is automatically added for cancelled-item KOTs, making them easy to distinguish from new orders. |
| 35 | KOT reprint settings | Controls whether the cashier is allowed to reprint a kitchen ticket after the order has been settled. If enabled, the manager configures a reprint print format and two printer assignments: one for dine-in reprints (table-order printer) and one for takeaway reprints (parcel-order printer). This is useful when the kitchen loses a ticket and needs a replacement copy. |
| 36 | Daily POS close enforcement | When enabled, the system checks at the start of each day whether the previous day's POS session was properly closed. If it wasn't, the cashier is blocked from opening a new session until the previous day is closed. The "day boundary" is configurable (e.g. 5:00 AM) to accommodate restaurants that operate past midnight. This ensures every shift is properly reconciled before the next one starts. |
| 37 | Reset order number daily | When enabled, the sequential order number (shown on kitchen tickets and receipts as "Order #1", "Order #2", etc.) resets to 1 at the start of each day. This makes it easy for kitchen staff to reference orders by a small, daily-resetting number rather than a long invoice ID. If disabled, the order number continues incrementing across days. |
| 38 | Multiple cashier mode | Enables a main-cashier-plus-sub-cashier workflow. One user is designated the "main cashier" (the owner or shift supervisor), and one or more other users are "sub-cashiers". Each sub-cashier has their own POS opening and closing entry with their own float. At end of shift, each sub-cashier closes their own session, and the main cashier's closing entry aggregates all sub-cashier totals. This is useful when the restaurant has multiple tills or when the bar and dining area have separate cashiers. |
| 39 | View all order statuses | Controls which order status filters appear on the orders screen. By default, only "Draft" and "Unbilled" are shown. When this toggle is enabled, the cashier can also filter by "Paid", "Consolidated", and "Return". This is typically enabled only for managers who need to see the full order history, not for front-line cashiers who only need to see active orders. |
| 40 | Paid order display limit | Controls how many "Recently Paid" orders are shown on the orders screen. Since a busy restaurant can have hundreds of paid orders in a day, showing all of them would be overwhelming. This setting limits the list to a manageable number (e.g. 20) so the cashier can quickly verify a recent payment without scrolling through hundreds of old orders. |
| 41 | Edit order type on past orders | When enabled, the cashier can change the order type of an existing order (e.g. change a Take Away to Delivery) after it has been created. This is useful when a customer changes their mind about how they want to receive their order. If disabled, the order type is locked once the order is created. |
| 42 | Remove items after print | Controls whether items can be removed from an order after the receipt has been printed. By default, printing locks the order — items cannot be removed or have their quantity reduced. This prevents a cashier from printing a receipt, secretly removing an item, and pocketing the difference. If the manager trusts the cashiers, they can enable this to allow corrections after printing. |
| 43 | Role-based billing | Restricts who can process payments and settle orders. Only users with a role listed in the POS profile's "role_allowed_for_billing" field can click the "Payment" button. For example, a waiter might be allowed to take orders but not process payments — only the cashier can do that. This separation of duties is important for cash handling security. |
| 44 | Role-restricted table orders | Restricts who can create Dine In (table) orders. Only users with a role listed in this field can select the "Dine In" order type. For example, a bar cashier might be restricted from taking dining room orders — they can only process Take Away and Delivery. This prevents staff from operating outside their assigned area. |
| 45 | Notification recipients | Defines which roles receive a notification when an order is delayed (the kitchen hasn't processed the ticket within the configured warning time). For example, the manager and the head chef might be notified. Each recipient role is a row in a child table on the POS profile. When a delay is detected, every user with that role gets a system notification. |
| 46 | Applicable users | Lists the users who are assigned to this POS profile. Each user row has a "default" flag — a user can have only one default profile per company. When a user logs in, the system loads their default POS profile automatically. This is how the system knows which terminal configuration, payment methods, and item groups to show each user. |
| 47 | Cost center mandatory | The POS profile must have a cost center specified. The cost center is the accounting dimension that all revenue and expenses from this terminal are posted against. Without it, the accounting entries would be unclassified, making it impossible to track profitability per terminal or per area. This validation prevents the profile from being saved without a cost center. |

### A5. Aggregator (Food Delivery Platform) Support

| # | Feature | What it does |
|---|---|---|
| 48 | Aggregator settings | Maps each food delivery platform (e.g. Uber Eats, Glovo, Jumia Food) to a customer record, a default price list, and a default payment method. When an order comes in from an aggregator, the system uses these settings to automatically select the right prices and payment mode. Each aggregator is configured per branch, so different branches can work with different platforms. |
| 49 | Aggregator menu | Fetches the menu items available for a specific aggregator, using that aggregator's price list. This means the aggregator might see a different set of items or different prices than a walk-in customer. For example, an aggregator might have a higher price to cover the platform's commission. When the cashier selects an aggregator as the order type, the POS loads the aggregator-specific menu. |
| 50 | Aggregator payment mode | Each aggregator has a configured default payment method (e.g. "Bank Transfer" for Uber Eats, "Cash" for Glovo). When an aggregator order is settled, the payment is automatically attributed to this method. This simplifies reconciliation — the manager can see at a glance how much revenue came through each platform. |
| 51 | Aggregator invoice numbering | Aggregator orders use a separate invoice numbering prefix (e.g. "AGR-0001") to distinguish them from regular orders. This makes it easy to filter aggregator orders in reports and accounting. The prefix is set on the restaurant configuration. |
| 52 | Aggregator unpaid orders | A branch-level option that makes aggregator orders unpaid (credit sales) instead of paid. This is useful when the aggregator pays the restaurant in a lump sum at the end of the week rather than per order. The order is recorded as a sale with an outstanding balance, and the lump-sum payment is recorded separately when it arrives. |
| 53 | Aggregator tax removal | A branch-level option that removes all taxes from aggregator orders. Some aggregators handle tax themselves and require the restaurant to send tax-free invoices. When this is enabled, the system clears the tax template and tax lines from aggregator orders automatically. |
| 54 | Aggregator order number prefix | Aggregator orders get an "AGR -" prefix on their sequential order number (e.g. "AGR - 1", "AGR - 2"). This makes it easy for kitchen staff to identify aggregator orders on kitchen tickets and handle them appropriately (e.g. packaging them for delivery pickup). |

### A6. Order Management (Backend)

| # | Feature | What it does |
|---|---|---|
| 55 | Order sync | The core function that creates or updates an order. When the cashier clicks "Add New Order" or "Update Order" on the POS screen, this function receives the order data (items, quantities, customer, table, order type, etc.) and creates a draft POS Invoice in the database. It sets the selling prices from the menu, assigns the waiter and cashier, marks the table as occupied, and triggers kitchen/bar ticket generation. If the order already exists (the cashier is editing), it updates the existing draft invoice instead of creating a new one. |
| 56 | Get table order | When a waiter selects an occupied table, this function finds the existing draft invoice linked to that table and loads its items into the POS screen so the waiter can add more items or modify the order. If the table has no existing draft invoice, it creates a new one. This is what makes the "click a table to continue an order" flow work. |
| 57 | Order type detection | When an order is placed for a table, the system automatically determines whether it's a Dine In or Take Away order based on the table's `is_take_away` flag. If the table is a regular dining table, the order type is set to "Dine In". If the table is a virtual takeaway table, the order type is set to "Take Away". This eliminates a manual step for the cashier. |
| 58 | Table restriction | Prevents a second draft invoice from being created for a table that already has an unprinted one. If a table has an open order (draft invoice, not yet printed), the system rejects any attempt to create a new order for that table. The cashier must either continue the existing order or print and settle it first. This prevents duplicate orders and confusion about which order belongs to which table. |
| 59 | Price list resolution | Determines which price list to use for an order, in this priority: 1) If the order is from an aggregator, use the aggregator's price list. 2) If the restaurant uses room-wise menus, use the price list for the menu assigned to the table's room. 3) If the restaurant uses order-type-wise menus, use the price list for the order type's menu. 4) Otherwise, use the active menu's price list. This ensures the customer is always charged the correct price based on where they're sitting and how they ordered. |
| 60 | Invoice print before submit | Dine-in orders must be printed (the receipt must be generated) before they can be submitted (paid and finalised). This prevents a scenario where a customer eats, pays, and leaves without a receipt. The system blocks the submit action and shows an error message: "Printing the invoice is mandatory before submitting." This rule applies only to dine-in orders; takeaway orders can be submitted without printing. |
| 61 | Item modification lock | After an invoice is printed, items cannot be removed from the order and quantities cannot be reduced. This is a fraud prevention measure — it stops a cashier from printing a receipt showing 5 items, then removing 2 items and pocketing the difference. The manager can disable this lock by enabling "Remove items after print" on the POS profile, but by default it is on. |
| 62 | Spend time calculation | When an order is submitted, the system calculates the total time the customer spent from order creation to payment. This is stored on the invoice and can be used in reports to analyse table turnover time, average dining duration, and peak-hour efficiency. The time is calculated as the difference between the invoice creation timestamp and the submission timestamp. |
| 63 | Table status on delete | When an invoice is deleted (not cancelled — deleted before it was ever submitted), the associated table is freed: its occupied flag is set to 0 and its latest invoice time is cleared. This makes the table available for new orders again. This only applies to draft invoices that haven't been printed or submitted. |
| 64 | Sequential order numbering | Each POS invoice gets a sequential order number (e.g. 1, 2, 3) that is unique within the current POS shift. This number is displayed on kitchen tickets, bar tickets, and receipts as "Order #1" — it's much easier for kitchen staff to call out than the full invoice ID. If "Reset order number daily" is enabled, the counter resets to 1 at the start of each day. |
| 65 | Table transfer | Allows the waiter to move an order from one table to another within the same room. This is useful when a customer wants to move to a different table (e.g. from a small table near the door to a larger one by the window). The system updates the table reference on the invoice, marks the old table as free, marks the new table as occupied, and updates any existing kitchen tickets to reference the new table. |
| 66 | Captain/waiter transfer | Allows reassigning the waiter (captain) on an open order. This is useful at shift changes or when a waiter goes on break and another takes over their tables. The system updates the waiter field on the invoice. If multiple-cashier mode is enabled, the system validates that the new waiter is assigned to the same room. |
| 67 | Cancel order | Cancels a POS invoice. The system frees the associated table (marks it as available), cancels all related kitchen/bar tickets, sets the invoice status to "Cancelled", and records the cancellation reason entered by the cashier. The cashier must provide a reason for the cancellation, which is stored for audit purposes. Only users with cancel permission can perform this action. |
| 68 | Cancel KOT | When an order is cancelled, the system creates a "Cancelled"-type kitchen ticket containing all the items from the order. This ticket is sent to the kitchen printer so the kitchen staff know to stop preparing those items. Then, all previously generated New/Modified KOTs for that invoice are set to cancelled status. This ensures the kitchen is always aware of cancellations. |
| 69 | Settle order | The final step in the order lifecycle. This function takes the draft invoice, applies any discount the cashier entered, replaces the placeholder payment with the actual payment details (method, amount), saves the invoice, and submits it (changes its status from Draft to Submitted). Once submitted, the invoice is immutable — it can only be cancelled, not edited. The table is freed, and the sale is recorded in the accounting system. |
| 70 | Customer favourite items | When a customer is selected on the POS, the system looks through their past orders and returns the top 3 items they have ordered more than once. These are displayed on the customer selection screen as "favourite items", helping the cashier suggest items the customer is likely to want. This improves service speed for regular customers. |
| 71 | Concurrent modification check | Before saving an order update, the system checks whether the invoice has been modified by someone else since the cashier last loaded it. It compares the `modified_time` timestamp sent from the POS with the invoice's actual `modified` timestamp in the database. If they don't match, it means another user (or the system) has changed the order in the meantime, and the update is rejected. This prevents lost updates when multiple staff members work on the same order simultaneously. |
| 72 | Billing role check | Before syncing an order, the system checks whether the current user has a role that is allowed to process billing (listed in the POS profile's `role_allowed_for_billing`). If the user doesn't have the role, the order is saved as a draft but cannot be submitted for payment. This enforces the separation between order-taking (waiter) and payment-processing (cashier). |

### A7. Kitchen & Bar Ticket System

| # | Feature | What it does |
|---|---|---|
| 73 | Ticket generation | When an order is synced (created or updated), the system compares the current items with the previous items on the invoice. It identifies three categories: 1) New items (items that weren't on the previous version), 2) Modified items (items whose quantity increased), 3) Cancelled items (items that were removed or whose quantity decreased). For each category, a separate ticket is generated with the appropriate type label: "New Order", "Order Modified", or "Partially cancelled". This tells the kitchen exactly what changed without reprinting the entire order. |
| 74 | Ticket item diffing | The comparison engine that determines what changed between two versions of an order. For each item, it checks: is this item new (not in the previous version)? Was the quantity increased (more than before)? Was the quantity decreased (less than before)? Was the item removed entirely? The result is a list of positive-delta items (to print as new/added) and negative-delta items (to print as cancelled/reduced). This precise diffing means the kitchen only sees what actually changed, not a full reprint. |
| 75 | Ticket routing by department | Each item in the order is checked against the production unit's item groups. Food items (in the kitchen's item groups) are routed to the kitchen printer. Drink items (in the bar's item groups) are routed to the bar printer. If an order contains both food and drinks, two separate tickets are generated — one for the kitchen and one for the bar. Each ticket only contains the items relevant to that station. This is the core of the departmental split: the kitchen never sees drink orders, and the bar never sees food orders. |
| 76 | Ticket type detection | If a ticket already exists for a given invoice and production unit (e.g. the kitchen already has a ticket for table T1's order), and the order is updated with more food items, the new ticket is labelled "Order Modified" instead of "New Order". This tells the kitchen that this is an addition to an existing order, not a brand new one. The kitchen can then merge it with the existing preparation. |
| 77 | Cancel ticket creation | When items are removed from an order or their quantity is reduced, a "Partially cancelled" ticket is generated. This ticket lists the cancelled items with their cancelled quantity (the amount removed) and the remaining quantity (what's still being prepared). It also references the original ticket number(s) so the kitchen can cross-reference. The cancel ticket is printed to the same station (kitchen or bar) that received the original order. |
| 78 | Ticket reprint | Allows the cashier to reprint a kitchen or bar ticket for a settled order. This is useful when the kitchen loses a physical ticket and needs a replacement. The reprint uses the configured reprint print format and selects the appropriate printer (kitchen or bar) based on the order type and department. The manager must enable reprint on the POS profile; it is disabled by default to prevent ticket spam. |
| 79 | Duplicate ticket detection | A background job that runs every minute and checks for draft invoices that were created 1-5 minutes ago but have no kitchen/bar ticket. If it finds any, it generates "Duplicate"-type tickets for them. This catches cases where the ticket generation failed during order sync (e.g. due to a transient error). Each duplicate ticket is logged in the KOT error log for audit purposes, so the manager can investigate why the original ticket wasn't generated. |
| 80 | Ticket error log | An audit trail record created every time the duplicate-ticket detection job generates a ticket. It records the ticket ID, the invoice ID, and the invoice creation time. This allows the manager to review how often tickets fail to generate automatically and investigate the root cause (e.g. a misconfigured production unit, a network issue with the printer). |
| 81 | Ticket delay notification | When a kitchen/bar ticket has been generated but not processed within the configured warning time (e.g. 15 minutes), the system sends a notification to the configured recipient roles (e.g. manager, head chef). | 99 | Sub-cashier closing validation | The system enforces that all sub-cashiers must close their sessions before the main cashier can close. | 101 | Cashier room assignment | When a POS opening entry is created, the system automatically sets the cashier's room based on their `URY User` assignment. This ensures every day's sales are properly reconciled before the next day begins. |
| 103 | POS opening check | A simple check that returns whether an open POS session exists for the current user's branch. The alert appears on the back office dashboard. |
| 131 | Safety stock | A minimum stock level that should always be maintained as a buffer against demand spikes or supply delays. If stock falls below the safety stock level, the system shows a more urgent alert. | 132 | Stock ledger entry | An immutable (never-changing) record of every stock movement. This is the source of truth for all stock reporting. |
| 133 | Stock entry | A document for recording manual stock movements. | 134 | Warehouse | A physical or logical location where stock is kept. | 135 | Stock reconciliation | The stocktake / physical inventory count process. The manager counts the actual stock in each warehouse and enters the counted quantities into the system. | 136 | Purchase receipt | Records the receipt of goods from a supplier. When a delivery arrives, the storekeeper creates a purchase receipt listing the items, quantities, and rates. Once received, the items are immediately available for sale on the POS. |
| 137 | Stock availability check | Before allowing an item to be added to an order, the system checks whether it's in stock. | 138 | Product bundles | A "combo meal" feature where a single item (e.g. "Chicken Combo") automatically expands into its component items (e.g. Chicken, Fries, Drink) when added to the cart. | 139 | Valuation method | Controls how the system calculates the cost of items when they're sold or transferred. ### A16. Document Workflow & Audit

| # | Feature | What it does |
|---|---|---|
| 179 | Submit/cancel workflow | Every financial document (orders, payments, stock entries) goes through a three-state lifecycle: Draft → Submitted → Cancelled. In Draft, the document can be freely edited. Once Submitted, it is locked — no field can be changed. If a mistake is found, the document is Cancelled, which creates a reversal entry (a mirror-image entry that undoes the financial impact) rather than deleting the document. This ensures a complete audit trail — you can always see what was done, when, and by whom. |
| 180 | Immutable audit trail | Orders, payments, and stock ledger entries have a `status` field with values DRAFT, SUBMITTED, or CANCELLED. Once a record is SUBMITTED, it is never updated — only a new CANCELLED record can reverse it. This is critical for financial integrity: if an order is submitted and paid, the record of that payment can never be altered or deleted. Any correction must be made through a new cancelling/reversing document, leaving the original intact. This is the same principle used by ERPNext for all financial documents. |
| 181 | Amendment chain | When a submitted document is cancelled (because it contained an error), the manager can "amend" it. Amendment creates a new document that is a copy of the cancelled one, but in Draft status so it can be corrected. The new document stores a reference to the original (`amended_from`). This maintains the link between the original (incorrect) document and the corrected version, so an auditor can trace the full history. |
| 182 | Track changes | For critical documents (orders, payments, menus), the system tracks every field-level change: what the field was changed from, what it was changed to, who changed it, and when. This change history is visible on the document's detail page in the back office. This is useful for investigating discrepancies — e.g. "who changed the price of this item from 1,500 to 1,000 and when?" |
| 183 | Cancel permission | The cancel-order button on the POS is only shown to users who have cancel permission on POS invoices. The system checks the user's permissions before displaying the button. This prevents waiters or junior staff from cancelling orders without manager approval. |
| 184 | Role-based button visibility | Certain POS buttons (cancel order, KOT reprint, table transfer, captain transfer) are only visible to users with the appropriate role. The system checks the user's roles against the POS profile configuration and shows or hides buttons accordingly. This keeps the POS screen clean for junior staff while giving senior staff access to advanced operations. |

### D4. Data Integrity & Validation

| # | Feature | What it does |
|---|---|---|
| 289 | Search input sanitisation | All search inputs on the POS are validated: maximum 100 characters, and only alphanumeric characters plus spaces, hyphens, underscores, @, and periods are allowed. Any other characters are rejected with an error message. This prevents SQL injection and XSS attacks through search fields. |
| 290 | Duplicate invoice prevention | The system prevents creating a second draft invoice for a table that already has an unprinted one. If a waiter tries to start a new order for a table with an existing open order, they see: "Table T1 has an existing invoice." They must continue the existing order or print and settle it first. This prevents duplicate orders and billing confusion. |
| 291 | Payment method validation | The POS profile must have at least one payment method configured, exactly one of which must be marked as the default. Each payment method must have a GL account configured for the company. These validations are enforced when the POS profile is saved, preventing misconfigured terminals from accepting payments they can't account for. |
| 292 | Stock validation | When an item is added to an order, the system can check whether it's in stock. The available quantity is calculated as: current stock in the warehouse minus reserved quantity (items on other submitted-but-unconsolidated POS invoices). If the item is out of stock, the cashier sees a warning. The manager can configure whether this check happens in real-time (on every item click) or only on save. |
| 293 | Concurrent modification detection | Before saving an order update, the system checks whether the invoice has been modified since the cashier last loaded it. | 294 | Invoice print before submit | For dine-in orders, the receipt must be printed before the order can be submitted (paid). | 295 | Item lock after print | After an invoice is printed, items cannot be removed and quantities cannot be reduced (unless the manager has explicitly enabled "Remove items after print"). ## E. ARCHITECTURE CONSTRAINTRAINTS

| # | Feature | What it does |
|---|---|---|
| 296 | Local network only (Phase 1) | The entire system runs on the cashier desktop and the local network. Django serves the POS and back office on the local WiFi. All operations — ordering, printing, inventory, reports — work without any internet connection. The owner can access the back office from any device (phone, laptop, tablet) connected to the same WiFi network inside the restaurant. No cloud, no external servers, no internet dependency. |
| 297 | Django + HTMX + Tailwind + Alpine.js | The frontend is built entirely with Django templates enhanced by HTMX (for partial page updates without full reloads), Tailwind CSS (for styling), and Alpine.js (for lightweight client-side interactions like dropdowns and modals). No React, no Vue, no Django REST Framework, no Socket.io. This keeps the stack simple, fast, and maintainable by a single developer. |
| 298 | PostgreSQL | The database is PostgreSQL, not SQLite. PostgreSQL handles concurrent access better (important when multiple cashiers are using the system simultaneously), supports advanced queries for reporting, and is more robust for financial data. |
| 299 | DecimalField for all money | All monetary values (prices, totals, discounts, payments, balances) are stored as `DecimalField` in the database, never `FloatField`. Floating-point numbers can introduce rounding errors (e.g. 0.1 + 0.2 = 0.30000000000000004), which is unacceptable for financial data. DecimalField stores exact decimal values, ensuring naira amounts are always precise. |
| 300 | No CASCADE on financial records | Orders, payments, and stock ledger entries never use `CASCADE` delete on their foreign keys. If a referenced record (e.g. a customer or an item) is deleted, the financial record is preserved (the foreign key is set to NULL or the deletion is blocked). This ensures the financial audit trail can never be broken by a cascading delete. |
| 301 | Immutable submitted records | Once a financial document (order, payment, stock entry) is submitted, it cannot be edited. Any correction requires a new cancelling document that creates a reversal entry. This is the same principle used by ERPNext and ensures a complete, tamper-proof audit trail. |
